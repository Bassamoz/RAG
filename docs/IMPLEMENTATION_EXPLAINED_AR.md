# شرح التنفيذ بالعربية

## ما أُنجز فعلًا

في 00 فُكت الحزمة داخل المجلد الحالي، ودُققت المواصفات والبحث والموجود، وأُنتجت وثائق وخطة ومخططات وحالة قابلة للاستئناف. الملف y.py بقي فارغًا كما كان. لا شفرة تطبيق أو endpoints أو قواعد بيانات أو migrations منفذة؛ scripts هنا أدوات توثيق وتحقق وليست backend.

## كيف ستتدفق البيانات

المستخدم يدخل البريد؛ BFF يطلب رمز المزود ويتحقق منه قبل إنشاء جلسة خادم. التفويض يحدد المنشأة والمتجر. المعرفة تدخل الحجر والتحقق ثم الاستخراج والتقسيم والتضمين، وتُنشر النسخة بعد مراجعة. عند سؤال مثل «هل يتوفر SKU-A باللون الأسود وما سياسة إرجاعه؟» يحدد المنسق المتغير، يسترجع BM25 وcosine ثم RRF وCross-Encoder للسياسة والوصف، ويقرأ التوفر الحالي من أداة المتجر في production. عند فشل الأداة لا يؤكد مخزونًا قديمًا. الجواب يتحقق من المصادر والنطاق وحالة المحادثة قبل الإرسال؛ takeover يسقط أي رد bot قديم. هذا مثال تصميم لا طلب API مجرب.

## لماذا هذه القرارات

بنية واحدة تمنع تكرار RAG بين الويب وWhatsApp؛ RLS والتفويض وفهارس المتجر تمنع اعتماد العزل على prompt. FAISS وLlama 3.1 8B محفوظان علميًا، وpgvector ونموذج إنتاج configurable توسع منفصل. ADRs تبين البدائل وحدود كل قرار. المخططات في ARCHITECTURE مقصودة وليست إثبات تكامل.

## التشغيل والتحقق

لفحص سجلات هذه المرحلة: `python -X utf8 scripts/validate_phase00.py`. استخراج البحث استعمل PyMuPDF في .venv (أداة تدقيق فقط)؛ النص والصور محفوظة في evidence. فشل طباعة النص أولًا بسبب cp1256 ثم نجحت إعادة التنفيذ بـ`-X utf8`. سجل الفحوص الفعلية في تقرير المرحلة وvalidation.json؛ اختبارات الميزات وخططها في TESTING، لا نتيجة pass لها.

## حدود فعلية

غياب git يمنع commit identifier؛ يُستخدم SHA256 artifact manifest للمراجعة. الحسابات والترخيص والأجهزة غير متحققة، وMeta طلبت دخولًا للوثائق العامة المسترجعة. لا رسالة أو بريد أو نموذج شُغل حيًا. الشاشات صلاحيات مقترحة لا منتج جاهز؛ الخط asset_required. التالي 01 عند طلب المستخدم فقط.

## أساس المرحلة 01 ومتابعة التشغيل

الموجود الآن تطبيق واحد في apps/web وapps/api، وعامل من حزمة API نفسها. صفحة الإعداد تقرأ الجاهزية عبر عميل OpenAPI مولد وتعرض حالة الاتصال الحقيقية. health لسلامة العملية فقط؛ ready يفحص دور DB المحدود وrevision0001 وRedis ومستهلك طابور البيئة قبل200. الأخطاء تحمل code/message/trace_id، وسجل الطلب allowlist لا يشمل body أو secrets.

Alembic يدير app.users/tenants/memberships/stores وpgvector فقط؛ لا يدير auth المملوك لـSupabase. runtime read-only بلا superuser أو bypassrls، وscoped_session يضبط سياق RLS ضمن transaction. اختبارات PostgreSQL الفعلية أثبتت منع قراءة متجر مستأجر آخر ومسح السياق عند إعادة استخدام pool. ربط هذا السياق بهوية موثوقة وعضوية فعلية جزء02؛ لا API بيانات محمية مضافة في01.

كان فشل Docker القديم متعلقًا بالبيئة. بعد تجهيز المستخدم WSL2 وDocker Desktop، أثبت الفحص أن sandbox يعمل بحساب آخر لا يملك إعداد Docker أو named pipe، بينما المضيف المصرح به يصل إلى Engine/Compose. لم نعد تثبيت Docker ولم نغير الصلاحيات. سكربت diagnose_runtime يوثق المقارنة دون أسرار.

اختبارات التكامل كشفت خللًا محددًا: worker.control.ping يثبت وجود عامل على Redis لكنه قد يستهلك طابور staging بينما API في dev. استُبدل بفحص active_queues لطابور البيئة المحدد، مع مهلة. دليل red أثبت Readiness200 الخاطئ، ثم green أثبت503 للبيئة الخاطئة و200 للبيئة الصحيحة. هذا فحص جاهزية أولي؛ تنفيذ المهمة الفعلي مثبت باختبار roundtrip منفصل.

المسار المحلي يبدأ Supabase واحدًا لـPostgres/Auth/Storage، ثم migration وتهيئة الدور، ثم Redis/API/worker/web. verify_development يأخذ baseline قبل أول تشغيل لقاعدة موجودة، ويعيد أمر التشغيل مع مقارنة بصمات الصفوف، ويحذف صف الاختبار الخاص به فقط. لا reset أو بيانات demo. اكتمل هذا المسار فعليًا: Health وReadiness والويب200 وCelery roundtrip، مع بقاء الصفوف متطابقة في التشغيلين. بعد finally عادت الصفوف إلى عددها السابق0 في هذه البداية الجديدة، وظهر revision0001 وpgvector0.8.2 ومخططا auth/storage. صور API والويب بُنيت وعملت على Linux بمستخدمين غير root. حفظنا الحالة السابقة والتقرير والأدلة في evidence/phase-01.

نتائج هذه المتابعة: أربع حالات تكامل حقيقية ناجحة، وclean checkout محلي مع16 اختبار Python وخمسة TypeScript ناجحة وtypecheck، وRuff/mypy/OpenAPI، وبناء الحاويات والتشغيل المتكرر. اختبارات checkout كشفت توريث متغيرات Git وتعارض صلاحيات Temp بين حسابي sandbox والمضيف؛ عُزلت البيئة ومجلد pytest وأعيد الفحص دون تغيير ACL أو عتبة اختبار. تقرير01 معتمد محليًا فقط؛ لا تجربة مزود بريد خارجي أو سلة/زد/Meta/AI/SMS، ولا تحقق هوية أو RAG أو نشر. القيود والتنبيه المتوسط لأداة lint في KNOWN_LIMITATIONS. validate_phase00 يراجع checkpoint التخطيط التاريخي، لا جاهزية المنتج الحالية. المرحلة02 لا تبدأ تلقائيًا.
