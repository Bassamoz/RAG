# المواصفات الملزمة لمنصة مستشار المتجر

الإصدار 1.0 — 2026-11-05. هذه مواصفات لبناء المشروع بواسطة Codex، وليست شهادة بأن برنامجًا قد بُني أو اختُبر. مرجع البحث الأصلي: `references/research.pdf` داخل هذه الحزمة.

## 1. الهدف وحدود العمل

ابنِ منصة ويب عربية/إنجليزية متعددة المستأجرين لخدمة عملاء المتاجر: موقع تعريفي، لوحة تاجر، مساحة موظف، إدارة منصة، نافذة محادثة قابلة للتضمين، وقناة WhatsApp Business رسمية. كل ميزة معلنة يجب أن تعمل من الواجهة إلى التخزين والصلاحيات والاختبارات. لا تنشئ متجرًا أو نظام دفع أو ERP.

التنفيذ مرحلي داخل مستودع واحد. خذ التعليمات الحالية للمستخدم وتعليمات المستودع بعين الاعتبار. الملف الحالي هو مصدر قرارات المنتج، و`RESEARCH_MAP.md` يميز ما ورد في البحث عن إضافات المنتج، و`REQUIREMENTS.md` يربط المتطلبات بالاختبارات.

لا تعِد ضمان 100% أو انعدام الثغرات أو اعتمادًا رسميًا. يمكن وصف إصدار بأنه مرشح للنشر فقط عند وجود أدلة الاختبارات والإعداد الحقيقي للخدمات المطلوبة. نجاح محاكاة مزود خارجي لا يثبت نجاح الربط معه.

## 2. سياسة الاستمرار دون إعادة البناء

قبل كل مرحلة اقرأ `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات `docs/adr/` والمتطلبات ذات الصلة. افحص git والوحدات الموجودة قبل التحرير. أكمل الموجود ولا تنشئ تطبيقًا ثانيًا أو خدمة مصادقة مكررة. لا تحذف عمل المستخدم أو تجرِ reset/force push أو إعادة تهيئة قاعدة بيانات قائمة.

إن تغيّر عقد API أو مخطط بيانات، وثّق السبب في ADR ونفذ migration متوافقة وحدّث المستهلكين واختباراتهم. لا تعِد توليد المشروع لتجاوز صعوبة. المكونات المولدة مثل عميل OpenAPI مصدرها واحد وتُولّد آليًا.

كل مرحلة تشتمل على التنفيذ الحقيقي واختبارات السلوك المناسبة وتحديث التوثيق. لا تؤجل الصلاحيات والتحقق من المدخلات إلى مرحلة الأمان الأخيرة. لا تكتب اختبارات شكلية تؤكد أن mock أعاد القيمة التي برمجتها فيه.

أنهِ المرحلة المطلوبة فقط ثم قدم تقريرها والخطوة التالية، دون طلب موافقة روتينية. إن غابت خدمة خارجية، أنجز الأجزاء المستقلة واختبارات العقود وسجل `blocked_external` للاختبار الحي؛ لا تضع `pass` ولا تُخفِ العائق. إذا كان المتطلب السابق ضروريًا، أصلح السابق أولًا أو اشرح العائق، ولا تبنِ اعتمادًا وهميًا.

حدّث الحالة بعد كل جزء مكتمل بحيث تستمر جلسة جديدة من ملفات المستودع. لا تخزن أسرارًا أو OTP أو بيانات عملاء في ملفات الحالة أو الشرح.

حدود الوحدات: identity، tenancy، stores، catalog، integrations، knowledge، retrieval، assistant، conversations، channels، support، analytics، lifecycle، operations. لا تجبر كل وحدة صغيرة على نمط معماري متكلف.

لا تستخدم Flutter أو ASP.NET Core كخلفية ثانية في هذا الإصدار. لا تضف Microservices أو Kubernetes أو Elasticsearch أو GPS أو PostGIS أو لوحة مزارعين أو بوابات التقسيط أو مزامنة بيانات حساسة دون اتصال. هذه ليست مطلوبة لوظيفة المشروع الحالية. يمكن استخدام CDN وCloudflare عند النشر؛ لا يُعد أي منهما بديلًا لأمان التطبيق أو دليلًا على تحمل غير مقاس.

## 4. ملفان تشغيليان يشتركان في الشفرة

`research`: بيانات ثابتة ذات إصدارات، FAISS متاح، لا وصول لطلبات حقيقية، لا أسعار حية مفترضة، لا إرسال خارجي تلقائي. إعادة إنتاج الخوارزميات والمقارنة المرجعية.

`production`: pgvector، متجران مستقلان على الأقل لإثبات العزل، ربط سلة وزد، استيراد متجر خاص، مزامنة، قنوات محادثة، أسعار ومخزون من مصادر تشغيلية موثوقة.

هما إعدادان لنفس الوحدات وليسا مشروعين. تغيير الخلفية المتجهية لا يغيّر قواعد التنظيف والتقسيم والتضمين وترتيب النتائج. لا تسمِّ فهرس FAISS قاعدة بيانات معاملات.

يذكر البحث حدودًا تمنع التكامل اللحظي في PDF ص14–15، ويذكر APIs في ص17؛ سجّل هذا التعارض وقرار توسيع المنتج. يذكر FAISS وLlama 3.1 8B؛ احتفظ بالتجربة المقابلة ولا تزعم أن pgvector أو نموذجًا آخر إعادة إنتاج مطابقة.

## 5. الهوية والجلسات والأدوار

الرحلة المطلوبة: إدخال البريد -> إرسال رمز بريد حقيقي -> إدخال الرمز والتحقق -> إنشاء/استعادة الجلسة -> الانضمام لمنشأة/إنشاء منشأة -> إعداد المتجر. البريد غير المتحقق لا يصل لبيانات اللوحة.

استخدم OTP الذي يديره Supabase، وقالب البريد الذي يعرض الرمز بدل Magic Link. اضبط مدة وانضباط إعادة الإرسال والمحاولات بما يدعمه المزود، واختبره. إرسال الرمز لا يعني تسجيل الدخول. لا تنشئ مولد رموز عشوائيًا آخر، ولا تعرض رموز الإنتاج في المتصفح أو السجلات. SMTP فعلي موثق شرط لاختبار البريد الحي؛ صندوق بريد محلي للاختبار فقط.

Email OTP دخول بعامل واحد؛ لا تسمه 2FA. أضف TOTP للأدوار platform_admin وtenant_owner، واسمح للأعضاء بتفعيله، مع فرض حالة AAL2 عند وجود عامل مفعّل وللعمليات الحساسة. صمم مسار فقدان العامل واسترداد الوصول بمراجعة موثقة، دون تجاوز MFA بالبريد وحده أو برمز ثابت.

اختر BFF server-only: متصفح اللوحة يحتفظ بمعرف جلسة عشوائي في Cookie `HttpOnly; Secure` مع SameSite ملائم، وCSRF للطلبات المغيرة. تُدار tokens الخاصة بـSupabase على الخادم باستخدام SDK الرسمي. تخزين refresh tokens مشفر، وتجديدها محكوم بقفل يمنع سباقات الطلبات. لا تخلط هذا المسار مع اعتماد SDK عميل يحتاج قراءة cookie نفسها. وثّق تنفيذ BFF واختبره.

FastAPI يتحقق من JWT الصادر عن المزود: التوقيع، الخوارزمية المسموحة، issuer، audience، exp، وربط subject بالمستخدم والجلسة الفعالة. تغيير الدور/تعليق الحساب/تسجيل الخروج يوقف الصلاحية في التطبيق، ولا يعتمد فقط على انتظار انتهاء JWT. لا تصمم JWT/تشفيرًا مخصصًا.

الأدوار: platform_admin، tenant_owner، tenant_admin، support_agent، analyst. سجل مصفوفة صلاحيات لكل endpoint وعملية. الدعوات مربوطة بالبريد المتحقق والمستأجر ولها انتهاء واستخدام واحد. لا يمكن سحب آخر مالك دون تعيين مالك آخر بطريقة آمنة.

رقم الاتصال الشخصي حقل مستقل بصيغة E.164 وحالة تحقق. تغييره يتطلب تحققًا من الرقم الجديد عبر مزود موثق؛ إن لم يُهيأ المزود لا يظهر موثقًا. تغيير البريد يتطلب تدفق المزود الآمن وإبطال الجلسات المناسبة. رقم WhatsApp Business وقناته كيانان مستقلان عن رقم ملف التاجر وعن MFA.

## 6. عزل المستأجرين

استنتج tenant/store من هوية موثقة وعضوية فعالة أو ربط قناة ثابت، لا من body يختاره العميل وحده. قد يملك المستخدم عضوية في أكثر من منشأة؛ تبديل المنشأة يعيد التحقق من العضوية.

PostgreSQL RLS على الجداول المملوكة للمستأجر، مع `tenant_id` و`store_id` حسب الحاجة، ومفاتيح أجنبية مركبة تمنع علاقات عابرة للمستأجرين. دور التشغيل ليس owner أو superuser ولا يحمل BYPASSRLS. استخدم سياق transaction-local بعد التحقق من الهوية لمنع تسرب السياق عبر pool؛ اختبر إعادة استخدام الاتصال بين متجرين. طبّق العزل أيضًا في SQLAlchemy والخدمات والعامل الخلفي.

لا تعرض مخطط التطبيق الحساس مباشرة عبر Data API بلا سياسات. `service_role` سر إداري محدود الاستخدام وليس مفتاح متصفح ولا تفويضًا عامًا لمسار البيانات. اعزل الوصول الإداري وسجله؛ لا تمنح مدير المنصة اطلاعًا روتينيًا مفتوحًا على محتوى المحادثات.

العزل يشمل pgvector وBM25 وFAISS وRedis وobject storage والتقارير والتصدير والبحث في المحادثات وملفات الرفع ورسائل WhatsApp والمهام. فهارس BM25/FAISS مستقلة لكل store/version، والتحقق النهائي من الحالة والصلاحية في قاعدة البيانات قبل استعمال المقطع إلزامي.

## 7. نموذج البيانات وعقود API

الجداول الأساسية المقترحة: users، sessions، tenants، memberships، invitations، stores، integrations، integration_secrets، categories، products، variants، store_policies، faqs، knowledge_sources، source_versions، knowledge_chunks، index_versions، conversations، messages، conversation_events، tickets، ticket_comments، assignments، channels، notifications، feedback، audit_events، usage_events، sync_jobs، webhook_inbox، outbox، export_jobs، deletion_requests، restore_jobs، evaluation_runs.

أنشئها عند حاجة المرحلة، لا كجداول فارغة بلا وظيفة. وسّع علاقات البحث للمستأجرين، ولا تنسخ `password_hash` من ERD لأن المصادقة مفوضة للمزوّد. السياسات العامة على مستوى المتجر، مع تخصيص منتج عند الحاجة؛ لا تكرر سياسة الشحن لكل منتج بلا داعٍ.

UUID للمعرفات، Decimal للأموال مع العملة، UTC للتخزين مع منطقة زمنية للعرض والتقارير، pagination وحدود أحجام وقوائم سماح للترتيب والبحث. optimistic concurrency للإعدادات والسجلات القابلة للتحرير. رسائل أخطاء آمنة لها code وtrace_id دون stack trace.

API إصدار `/api/v1`، OpenAPI مصدر العقد، وعميل TypeScript مولّد. تحقق من المدخلات والمخرجات؛ منع mass assignment. طبّق idempotency في العمليات التي قد تتكرر. حدّد unique keys للمعرفات الخارجية مقيدة بالمزوّد والمتجر. لا تُجرِ تكاملًا خارجيًا طويلًا داخل معاملة قاعدة البيانات.

## 8. البيانات والتكاملات

طرق الإضافة: Salla OAuth، Zid OAuth، Custom Store API موثقة، CSV/XLSX، وصفحات عامة مسموحة من نطاق مثبت الملكية/التفويض. الخانة تطلب الرابط وتكتشف المنصة مبدئيًا وتسمح بتصحيحها. الرابط ليس إثبات ملكية ولا تصريحًا لبيانات خاصة ولا وعدًا باستخراج كل موقع.

Salla وZid موصلان منفصلان خلف interface صغيرة: connect، refresh، fetch_products، fetch_variants، fetch_product، sync، disconnect، health؛ capability matrix للسياسات والمخزون والعروض والطلبات. اختبر حساب/متجر المزود مبكرًا. لا تخترع endpoint أو scope أو توقيع webhook مشتركًا بين المزودين؛ اتبع الوثائق الرسمية الحالية.

OAuth state عشوائي مرتبط بالجلسة والمستأجر واستخدام واحد، redirect allowlist، منع إعادة ربط متجر يخص مستأجرًا آخر. PKCE فقط حيث يدعمه المزود. tokens مشفرة، refresh مقفل، إلغاء الربط يبطل القدرة على الاستخدام.

استيراد أولي pagination، checkpoints، تقدم مرئي، retry/backoff/jitter، مراعاة Retry-After، وضبط ميزانية كل متجر. webhooks تتحقق حسب آلية المزود ثم تُحفظ بشكل متين قبل ACK وتُعالج خلفيًا. امنع التكرار، واعالج أحداثًا متأخرة/خارج الترتيب بالمراجعة وإعادة الجلب عند اللزوم. المزامنة الدورية تعوض الفقد.

كتالوج المتجر الخارجي مصدر الحقيقة؛ شاشة المنصة للعرض والتشخيص وتخصيص الظهور في المساعد. لا توحِ بأن تعديل سعر محلي سيعدل سلة/زد. CRUD كامل للمنتجات اليدوية والمعرفة والسياسات والإعدادات، مع فصل أي override معتمد عن الأصل.

احتفظ بالمتغيرات وSKU والأسعار/العملة والضرائب حين تتاح والتوفر والصور وروابط العميل ووقت المصدر وآخر مزامنة. لا ترسل cost_price أو أسرار كوبونات أو بيانات إدارية للنموذج. السعر النهائي للخصومات المشروطة يُحسم من مصدره عند الدفع؛ لا يضمن المساعد أهلية خصم غير متحقق منه.

## 9. المعرفة والفهرسة

مصادر: FAQ، نموذج معلومات المتجر، نص/Markdown، PDF نصي، DOCX، CSV/XLSX، URL محدد. CSV/XLSX ليست نصًا حرًا: mapping ومعاينة وتحقيق صفوف وتقرير أخطاء ومفاتيح تمنع التكرار. PDF المصور يُكتشف وتظهر حاجة OCR؛ لا تزعم استخراجه. يمكن إضافة OCR كخيار واضح بعد اختبار دقته.

pipeline حالات: uploaded -> quarantined/validated -> extracted -> normalized -> chunked -> embedded -> indexed -> review_ready -> published، مع failed/cancelled. استخدم حسب المصدر؛ لا تجعل ملفًا جديدًا منشورًا تلقائيًا دون إعداد واعتماد واضحين. أحجام وحدود موارد ونوع ملف ومكافحة zip bombs ووقت تنفيذ محدود؛ لا تنفذ macro أو تعليمات مستند.

تقسيم دلالي فعلي قابل للتفسير: حدود العناوين والجمل، الحفاظ على الشروط والاستثناءات، ثم إشارة تغير دلالي من embeddings عند الحاجة مع حد tokens/overlap موثق. لا تسمِّ التقسيم بالحروف Semantic Chunking. احتفظ بمقارنة baseline ثابتة للتقييم.

أصل النص محفوظ؛ normalization للبحث في حقل منفصل، ويدعم العربية/الإنجليزية والأرقام وSKU دون تدمير أسماء المنتجات. لا تطبق stemming إنجليزيًا على العربية. dedup بالمحتوى ضمن نطاق المتجر مع حفظ المصادر. Metadata: tenant/store/source/version/chunk/language/page_or_section/visibility/published_at/hash/model/dimensions.

نشر إصدار معرفة ذري: ابنِ الفهارس ثم بدّل مؤشر النسخة المنشورة. عند حذف/تعطيل مصدر يُمنع استخدامه فورًا بفلتر authoritative حتى لو تأخر حذف الفهرس؛ ثم تنظف كل نسخه وcache. تغيير embedding model/dimensions يقتضي إعادة فهرسة كاملة مع تبديل آمن؛ لا تخلط فضاءات متجهية.

الأولوية: بيانات تجارية حديثة معتمدة للحقول المتغيرة؛ سياسة منشورة فعالة التاريخ لأسئلة السياسة؛ تعارض غير محسوم -> توضيح/تحويل، لا اختيار صامت بالحدس. اجعل حداثة البيانات مرئية للتاجر.

## 10. الخوارزميات ومسار الإجابة

المسار الإلزامي: تحليل السؤال والسياق -> تحديد النية والكيانات ونطاق المتجر -> BM25 بالتوازي مع dense cosine -> دمج وإزالة تكرار -> Cross-Encoder -> اختيار السياق -> إجابة مقيدة -> تحقق -> إرسال أو امتناع/تحويل.

BM25: استخدم خوارزمية حقيقية مع k1 وb وIDF variant موثق؛ قيم البداية المقترحة k1=1.2 وb=0.75 قابلة للمعايرة على dev. `ts_rank` ليس BM25. لا تولّد scores وهمية. الفهرس إصدار منشور محفوظ بخريطة chunk IDs، checksum، tokenizer version، واستبدال ذري مع قفل وحذف cache قديم.

Dense: cosine للمتجهات من نفس النموذج والأبعاد؛ التعامل مع المتجه الصفري والمدخل الفارغ. pgvector cosine distance تُحوّل بدقة عند عرض similarity. FAISS يستخدم inner product مع تطبيع L2 لاستعادة cosine، ضمن فهرس متجر معزول. اختبر النتائج على vectors معلومة وقارن exact search قبل تفعيل ANN؛ راقب recall بعد فلاتر المستأجر.

RRF: `score(d) = sum(1 / (k + rank_i(d)))`، الرتب تبدأ من 1، وقيمة بداية k=60. اختبر الاتحاد والتكرار والقوائم الفارغة والتعادل؛ هذه إضافة هندسية لتحديد الدمج وليست معادلة مذكورة في البحث.

قيم بداية للتجربة وليست نتائج نهائية: 30 مرشحًا لكل مسار، اتحاد bounded، rerank لأفضل 30، وسياق 5–8 مقاطع وفق ميزانية tokens. عايرها على dev ولا تغيّر test set لتحسين النتيجة.

Cross-Encoder حقيقي يقرأ أزواج السؤال والمقطع؛ ثبّت revision واستخدم نموذجًا متعدد اللغات. لا تستبدله LLM judging أو cosine وتسميه Cross-Encoder. لا تنزّل أوزانًا من مصادر مجهولة ولا تفعّل trust_remote_code تلقائيًا. حمّل النموذج مرة لكل process مناسب، واضبط concurrency/memory/timeout. وثّق عدم توفره كتعطل؛ fallback صريح ومقاس وليس ادعاء اكتمال الخوارزمية.

النيات الأساسية: المنتج، الشحن، الإرجاع والاستبدال، الضمان، توصية منتج، سياسة متجر، FAQ، سؤال عام داخل النطاق. سياق الجلسة محدود ومعزول؛ إعادة صياغة السؤال تحفظ المقصود وSKU والنفي والميزانية، ولا تعيد استخدام حقائق سعر قديمة من السجل.

للحقول المتغيرة في production، أدوات read-only معرفة بخطط schemas: lookup_product، check_variant، verified_order_status عند توفر تحقق هوية مناسب. صلاحيات الأدوات على الخادم، ولا SQL حر أو URL حر يختاره النموذج. قبل الرد يتحقق النظام من السعر/المخزون وفق freshness policy؛ التعطل لا يتحول لتأكيد خاطئ.

الإجابة المنظمة: نص، source IDs، product IDs، answer_status، ومبرر تشغيلي مختصر مثل insufficient_evidence؛ لا تحفظ chain-of-thought. تحقق من أن المصادر منشورة ومملوكة للمتجر وأن بطاقات المنتجات مبنية على حقول موثوقة. التشابه أو score ليس احتمال صحة معايرًا.

المحتوى المسترجع غير موثوق كتعليمات. افصل سياسة النظام عن البيانات، وامنع تنفيذ أوامر في الوثائق أو تغيير الأدوار أو كشف أسرار. افحص الأرقام والوعود وروابط الخروج والبيانات الحساسة، واطلب توضيحًا أو امتنع عند نقص الدليل. التحقق يقلل الخطأ ولا يضمن انعدام الهلوسة.

## 11. المحادثة والموظف وWhatsApp

المحادثة لها آلة حالات: bot_active، handoff_pending، human_active، resolved/closed. كل رسالة لها ID/idempotency key وحالة إرسال. تزامن takeover/generation محكوم بـversion/epoch؛ إذا استلم الموظف أثناء توليد رد يُلغى/يُسقط رد البوت قبل الإرسال. لا ترجع السيطرة للبوت إلا بإجراء مصرح واضح.

حزمة التحويل: السبب، آخر رسائل لازمة، ملخص قابل للتحقق، المنتج/السياسة ذات الصلة، وحالة التحقق من هوية العميل. حالات التحويل: طلب الموظف، نقص المعرفة، غموض متكرر، فشل الأدوات أو الضوابط. الدعم غير المتاح يولد تذكرة مع توقع واقعي دون وعد زمني غير مهيأ.

الأسلوب يحدد يدويًا: رسمية، وضوح، طول، ترحيب واعتذار. خيار استخراج خصائص عامة من محادثات منزوعة الهوية بموافقة التاجر مع مراجعة بشرية؛ لا تحفظ بيانات الأشخاص في أمثلة الأسلوب ولا تنسخ الردود أو تعِد استخدامها كحقائق.

البحث يذكر نافذة أول رد 15–120 ثانية وتالٍ 15–60 ثانية في PDF ص103. نفذ timing policy قابلة للاختبار بساعة وهمية، ووضعها التجريبي اختياري. الإعداد التشغيلي الافتراضي يرسل بعد الجاهزية دون تأخير مصطنع. أرسل acknowledgment سريعًا، وحالة معالجة حقيقية، ولا تعِد نافذة أول رسالة لكل رسالة. لا تؤخر موظفًا أو رسالة أمنية، وألغِ ردًا مجدولًا إذا أصبح قديمًا. سجّل processing/queue/delivery/intentional_delay منفصلة.

Widget خفيف مع عزل CSS/iframe وسماح origins مضبوط وpostMessage origin checks، ومعرف عام لا يمنح وصولًا لبيانات خاصة. جلسة زائر مقيدة بمتجر ومحادثة، rate limiting، أزرار مساعدة وبطاقات منتجات وتقييم وطلب موظف. اختبر الجوال ومنع XSS في Markdown والروابط. لا ترسل نصًا غير متحقق منه عبر streaming ثم تزعم أن الفحص يحميه؛ استخدم status streaming ثم جوابًا متحققًا أو بروتوكول تحقق قبل كل جزء.

WhatsApp: Cloud API الرسمي مع Embedded Signup حيث تتوفر الموافقات، أو إعداد تجريبي رسمي موثق؛ لا QR لواتساب الشخصي ولا أتمتة WhatsApp Web. اربط WABA/phone_number_id بالمستأجر ربطًا خادميًا، ولا تثق برقم نصي يكتبه المستخدم لإثبات ملكية القناة. إدخال رقم لا يكفي للتفعيل.

تحقق webhook challenge وsignature حسب الوثائق، واستخدم inbox/outbox والـmessage IDs لمنع تكرار المعالجة. أعد ترتيب status events بأمان. التزم بنافذة خدمة العملاء والقوالب المعتمدة والاشتراك/الانسحاب والسياسات الحالية؛ راجع Meta عند التنفيذ لأن التفاصيل تتغير. لا ترسل حملات جماعية.

تمييز queued/sent/delivered/read/failed/unknown؛ timeout أثناء إرسال خارجي لا يُعاد عميانيًا عندما قد يكون المزود قد استلم الرسالة. اختبر recovery/reconciliation دون وعد exactly-once غير مدعوم. اربط الرد بنفس مسار RAG والتحويل البشري، لا بنسخة أخرى من المنطق.

معرفة رقم واتساب العميل أو رقم الطلب وحدها لا تثبت ملكيته للطلب. بيانات الطلب الخاصة تتطلب جلسة عميل موثوقة من المتجر أو تحققًا عبر قناة مسجلة لدى المتجر؛ إن تعذر ذلك تبقى الوظيفة غير متاحة ويحوّل لموظف.

## 12. الواجهات ونظام التصميم

العربية RTL افتراضيًا والإنجليزية LTR، ترجمة منظمة، تنسيق تواريخ/عملات حسب locale، وعزل اتجاه البريد وSKU والأكواد. لا تستخدم أيقونة وحدها لوظيفة غير واضحة.

لوحة الألوان الأساسية: `#F8F8F8` نحو 60% للمساحات، `#363638` نحو 30% للنص والبنية، `#B9F1E4` نحو 10% للإبراز. لون رابع اختياري `#B42318` للأخطاء والإجراءات الخطرة، ضمن نسبة الإبراز لا كنسبة إضافية. النسب إرشادية بصرية وليست اختبار عدّ بكسلات. الشعار وصور المنتجات محتوى مستثنى؛ لا تضف ألوان UI خامسة. استخدم النص والأيقونات والأنماط لحالات النجاح والتحذير، ولا تعتمد على اللون وحده.

النعناعي مع نص فحمي؛ لا نص فاتح فوق النعناعي. WCAG 2.2 AA: تباين 4.5:1 للنص العادي، 3:1 للكبير وعناصر UI المعنية، keyboard/focus/dialog semantics، labels، error association، reduced motion، zoom وإعادة التدفق. فحوص آلية مع فحص يدوي؛ لا تدّعِ شهادة وصول.

الخط المفضل الوحيد للهوية: ثمانية بملفات مرخصة يقدمها صاحب المشروع. لا تنزّل نسخة غير مرخصة أو تدّعِ توفره. إن غاب، سجل `asset_required`، واستعمل fallback نظامي للتطوير فقط مع بيان أن اعتماد الخط والتصميم النهائي ما زال معلقًا.

نظام spacing 4/8px، مقاييس typography محددة، مساحات بيضاء كافية، alignment ثابتة، action رئيسي واضح في كل شاشة، border/radius متناسقان، skeletons مناسبة. الهاتف 360/390px واللوحي 768px والسطح 1280/1440px؛ جداول الهاتف تتحول أو تُمرَّر ضمن حاويتها دون كسر الصفحة. اتجاه timeline والشريط الجانبي واعٍ للغة.

الصفحات: تعريف/تجربة، دخول/OTP/MFA/استرداد، إنشاء منشأة/دعوة، onboarding، overview، stores/integrations، catalog/variants، knowledge/sources/versions/FAQs/policies، assistant settings/playground، inbox/conversation، tickets، WhatsApp/channel installation، analytics/reports، notifications، team/roles، account/security/sessions، usage، trash/restore/export، وplatform administration.

لكل صفحة role/primary action/data source وحالات loading/empty/error/no_permission/success/partial/offline-reconnect حيث تنطبق. لا تجعل زرًا ظاهرًا بلا وظيفة؛ الميزة غير المهيأة تعرض setup أو unavailable مع السبب. لا بيانات تجريبية مخفية في production ولا رسوم بيانية وهمية.

## 13. التقارير والإدارة ودورة حياة البيانات

Overview وتقارير بمحدد متجر وفترة وقناة: حجم المحادثات، الحل الآلي بتعريف معلن، التحويلات، زمن الرد، التقييمات CSAT، الأسئلة غير المجابة، فشل المزامنة، tokens والتكلفة الفعلية إن توفرت أسعار موثقة. zero/null مختلفان؛ عند عدم وجود بيانات تظهر حالة فارغة.

تصدير CSV وXLSX وPDF وMarkdown للتقارير المناسبة، خلفيًا إذا كان كبيرًا، بروابط خاصة منتهية. احمِ CSV من formula injection، واختبر العربية والخطوط وRTL في PDF. لا تحسب انخفاض تذاكر الدعم أو زيادة المبيعات بلا baseline واقعي.

CRUD مع soft delete وسلة مهملات حيث يلزم: المعرفة اليدوية والسياسات وFAQs والمنتجات اليدوية والمحادثات حسب سياسة الاحتفاظ. restore لا يعيد نشر محتوى دون تحقق أو موافقة ولا يلغي إبطال token. إخفاء منتج خارجي من المساعد مختلف عن حذفه من متجره.

الحذف النهائي يتطلب صلاحية وإعادة تحقق وعرض النطاق؛ عملية قابلة للتتبع تحذف البيانات والملفات والمقاطع والمتجهات وفهارس البحث وcache وتمنع jobs المتأخرة من إحيائها. سجل طلب محو minimal، ولا تحفظ النص المحذوف داخل audit. لا تعد بمحو فوري من نسخ احتياطية غير قابلة للتعديل؛ وثّق انتهاءها وسياسة منع إعادة البيانات الممحوة عند الاستعادة.

نسخ احتياطي مشفر لقاعدة البيانات والملفات والإعدادات اللازمة، مع مفاتيح منفصلة وصلاحيات مقيدة. استرجاع فعلي إلى بيئة معزولة، checksums ومطابقة علاقات وصفوف وفهرسة وصلاحيات. قاعدة البيانات وحدها ليست نسخة ملفات التخزين. FAISS/BM25 يمكن إعادة بنائهما، مع حفظ manifests والنماذج/الإصدارات اللازمة.

التاجر يسترجع عناصر منشأته ويصدر بياناتها؛ الاسترجاع الكامل لقاعدة البيانات إجراء تشغيل إداري معزول، وليس زرًا متاحًا للتاجر. اعزل outbound أثناء restore حتى لا تعاد إرسال رسائل أو webhooks. أعد تطبيق سجل المحو الأحدث قبل فتح الخدمة، واختبر هذه الحالة.

## 14. الأمان والأدلة

نموذج تهديد يشمل BOLA/IDOR وBFLA، رفع الصلاحيات، JWT/session/OTP abuse، SQL injection، XSS/Markdown، CSRF، SSRF/DNS rebinding وredirects، traversal، رفع ملفات ضارة/كبيرة، formula injection، webhook forgery/replay، prompt injection/RAG poisoning، تسرب عبر cache/vector/export، وإساءة الاستخدام والتكلفة.

اربط الضوابط بمتطلبات OWASP ASVS الحالية ذات الصلة بهدف Level 2، وسجل المنطبق وغير المنطبق والأدلة؛ هذا هدف مراجعة لا اعتماد تلقائي. TLS وضبط headers وCSP/CORS، secrets manager أو حقن أسرار آمن، تدوير مفاتيح، تنقيح PII، حدود للطلبات والمهام والـtokens، least privilege، نسخ احتياطي وخطة استجابة للحوادث.

Crawler وموصل URL الخارجي: HTTPS/HTTP المسموحان فقط، منع loopback/private/link-local/metadata وIPv6 equivalents، إعادة التحقق بعد DNS وredirect ومنع rebinding بربط الاتصال بالوجهة المتحققة أو egress proxy موثوق. تفويض نطاق وأعداد صفحات ووقت/حجم/سرعة محدودة واحترام القيود؛ لا تجاوز تسجيل الدخول أو CAPTCHA.

فحوص أسرار وتبعيات وSAST وcontainer image وDAST في بيئة نملكها ببيانات اصطناعية. لا تشغّل فحصًا هجوميًا على سلة/زد/Meta أو متجر خارجي. اجمع النتائج مع الشدة وقابلية الاستغلال والإصلاح وإعادة الاختبار. لا تُخفِ الثغرات أو تحذف قاعدة فحص ليصبح التقرير أخضر.

## 15. استراتيجية الاختبارات والتقييم

اختبارات الوحدة للسياسات والخوارزميات ذات النتيجة المعروفة، integration مع PostgreSQL/pgvector/Redis وصلاحيات تشغيل حقيقية، contracts للموصلات، E2E لكل رحلة رئيسية، accessibility، security، migration، backup/restore، load/resilience، واختبارات نماذج حقيقية اختيارية بمفتاح وميزانية.

Fixtures تضم مستأجرين وثلاثة متاجر على الأقل، أدوارًا مختلفة، منتجًا متغيرًا، سياسة متعارضة، مصدرًا محذوفًا، webhook مكررًا، وملفًا خبيثًا اصطناعيًا. أضف tests للمنع كما تضيف للنجاح، ومنع وصول revoked session ورؤية archived/private chunks.

افصل deterministic CI عن real-provider وreal-model smoke. mocks عند حدود الشبكة مسموحة لاختبار الفشل؛ لا تسوّق نتائجها كجودة ذكاء اصطناعي أو تأكيد تفعيل بريد/واتساب. تخطي اختبار لغياب secret يعني `blocked_external` في gate المناسب.

التقييم: Amazon-combined كما ورد في البحث، مع revision/hash/license وschema/count موثقين عند التحميل؛ رقم 2,980 من البحث ليس فرضية دائمة. لا توزع dataset أو بيانات مشتقة قبل التحقق من شروطها. إذا لم تتضح، استخدم dataset اصطناعية موسومة للتطوير وسجل العائق الأكاديمي.

أسئلة عربية وإنجليزية، SKU، paraphrase، نفي، مقارنة وتوصية، غموض، خارج النطاق، عدم وجود معلومة، بيانات قديمة، injection وتسرب مستأجر. gold evidence وanswers ومراجعة بشرية، dev للمعايرة وtest مجمد، ومنع إدخال إجابات test الجاهزة في قاعدة المعرفة. منتجات corpus هي مصدر الدليل المسموح؛ عزل مجموعات الصياغات المتشابهة يمنع تسرب المعايرة.

المقاييس: Precision@K، Recall@K، MRR، ويمكن nDCG@K كإضافة، صحة الإجابة وFaithfulness ومعدل الادعاء غير المدعوم والامتناع الصحيح، زمن كل مرحلة وp50/p95، الكلفة، ونبرة الرد. RAGAS مساعد قياس بإعدادات ونموذج حكم موثقين، ولا يغني عن gold/human review.

Ablations: Llama 3.1 8B بلا استرجاع ومع المسار نفسه؛ BM25 فقط، dense فقط، hybrid دون reranker، hybrid+reranker، وguardrails ablation داخل بيئة بحث فقط. ثبّت النموذج والبيانات وباقي الإعدادات عند قياس أثر الاسترجاع. تجربة hosted model منفصلة، ولا تنسب فرق النماذج كله إلى RAG.

أي أهداف أداء/جودة تُثبت قبل الاختبار النهائي في `docs/ACCEPTANCE_BUDGETS.md` مع workload/hardware/dataset/version. لا تدّعِ آلاف المتزامنين دون قياس، ولا تغيّر العتبات بعد رؤية الفشل دون قرار معلن. التسرب بين المستأجرين في حالات الاختبار الحرجة يمنع الإصدار، حتى لو كانت نسب التغطية عالية.

## 16. النشر والتوثيق وشروط التسليم

حزم البناء immutable ومحددة الإصدار، non-root containers، health/readiness، graceful shutdown، حدود موارد، migration واحدة في كل نشر، فصل dev/staging/prod. `docker compose` وscript تشغيل موثق، مع مسار Windows/WSL2 ومسار Linux. استخدم Supabase المحلي عند الاختبار للبريد/Auth/Storage/Postgres إن أمكن، ولا تنشئ نسختين متضاربتين من قاعدة التطبيق.

النشر الأولي: خادم سحابي يدير الويب وAPI والعامل وRedis عبر Docker، وSupabase لقاعدة البيانات/Auth/Storage. domain/TLS وSMTP وprovider credentials وbackup destination متطلبات تشغيل، لا placeholders توصف بأنها إعداد مكتمل. Kubernetes وauto-scaling خارج النطاق حتى تثبت حاجة بالقياس.
