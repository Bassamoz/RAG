# المرحلة 18: بوابة الإصدار والتدقيق النهائي

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 17. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R01–R48.

## العمل المطلوب

1. راجع المشروع النهائي كما يراه مستخدم جديد. طابق كل صف من REQUIREMENTS_TRACEABILITY مع واجهة وكود واختبار ودليل. تحقق من عدم وجود زر بلا أثر أو endpoint بلا صلاحية أو mock/demo في مسار production.
2. افحص كل ادعاء في التوثيق: هل BM25/Cross-Encoder/FAISS نفذت فعليًا؟ هل البيانات حقيقية أم اصطناعية؟ هل Email OTP/سلة/زد/WhatsApp اختُبرت حيًا؟ هل تقارير التقييم تخص النسخة الحالية؟ صحح أي ادعاء زائد.
3. ثبّت release candidate commit/build ID. نفذ الفحوص النهائية اللازمة على تلك النسخة: build، regression paths الحرجة، tenancy، security scans المتأثرة، E2E smoke، restore evidence صالح لنفس schema، وreadiness للمزودين. نتيجة قديمة قبل تغيير مؤثر لا تكفي.
4. أصلح المشاكل موضعيًا، ثم أعد الفحوص المتأثرة. لا تبدأ architecture جديدة ولا تنشئ مشروعًا بديلًا ولا تحذف اختبارًا فاشلًا. التغيير الأخير يستلزم تحديث hash وأدلة البناء.
5. أنشئ `docs/RELEASE_READINESS.md` بجدول: feature/requirement، code status، local test، live test، evidence، blocker، القرار. الحالات: code_complete/local_verified/staging_verified/external_integrations_verified/production_ready/deployed. لا تمنح production_ready مع فحص حرج skipped أو ربط معلن لم يعمل.
6. تحقق أن التقارير لا تحتوي secrets/OTP/PII، وأن `.env.example` قابل للفهم، وملفات اختبار/fixtures لا تمس عملاء حقيقيين، وأن licenses/fonts/data provenance واضحة.
7. أعد قراءة `IMPLEMENTATION_EXPLAINED_AR.md` من منظور الطالب: أين تبدأ؟ ما دور كل وحدة؟ كيف تعمل الخوارزميات؟ أين نعدل؟ كيف نشغل ونختبر وننشر ونسترجع؟ ما الحدود؟ أصلح الفجوات وأضف مثالًا واقعيًا موثقًا لا نتيجة مختلقة.
8. أخرج handover: قائمة الميزات المكتملة، حدودها، روابط/مسارات التقارير، خطوات التشغيل والنشر، المتطلبات الخارجية الناقصة، ترتيب العمل المتبقي. إذا بقي عائق اذكر إجراءً محددًا لحله، ولا تستبدله بعبارة «كل شيء جاهز».

## بوابة القرار

- جميع فحوص الأمن والعزل والرحلات الأساسية ناجحة على الإصدار المقصود، ولا ثغرات high/critical قابلة للاستغلال معلومة غير معالجة.
- كل تكامل مطلوب في نطاق الإصدار له اختبار حي موثق؛ وإلا تُمنع دعوى جاهزية النطاق الكامل.
- الاختبارات البحثية المطلوبة لها نتائج فعلية أو تظهر صراحة غير منفذة، ولا نتيجة مولدة لغويًا لتجميل التقرير.
- تمرين الاستعادة والاحتفاظ والمحو مثبت، وخطة نشر/تراجع قابلة للتنفيذ، والأداء ضمن budget المعلن أو معلن أنه لم يبلغ الهدف.

أجب بالعربية بوضوح عن ما بُني وكيف اختُبر وما بقي. لا تطلب تأكيدًا لعمل روتيني منجز، ولا تمنح ضمان 100% أو شهادة أمان/امتثال لم تصدر.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
