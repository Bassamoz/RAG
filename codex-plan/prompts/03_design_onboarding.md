# المرحلة 03: نظام التصميم والواجهات والإعداد الأول

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 02. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R08، R09، R47.

## العمل المطلوب

1. حوّل مواصفات الألوان 60/30/10 إلى tokens موحدة؛ الحد الأقصى أربعة ألوان UI أساسية، والحالات مفهومة بالنص والأيقونة. طبّق ثمانية عند توفر ملفات مرخصة؛ سجل نقصها بدل تنزيل نسخة غير موثوقة.
2. ابنِ primitives قابلة للوصول: buttons، inputs، OTP input يدعم اللصق، dialogs، tables، pagination، tabs، alerts، dropdowns، skeletons وempty states. لا مكتبتين متداخلتين للمكونات نفسها.
3. طبق RTL/LTR وi18n، typography وspacing ومحاذاة ثابتة، focus visibility، keyboard navigation، labels، error descriptions، reduced motion وzoom/reflow. البريد وSKU وأكواد التحقق باتجاه واضح.
4. أنشئ navigation مبنية على الأدوار وصفحة تعريف وتجربة غير مخادعة، وواجهات الحساب الحالية، وshell لمساحة التاجر/الموظف/إدارة المنصة. الشاشات التي لم يُبنَ منطقها لا تعرض أرقامًا أو أزرار نجاح وهمية.
5. ابنِ onboarding محفوظًا: معلومات المنشأة -> متجر ورابط ونوع منصة -> حالة الربط -> المعرفة -> تخصيص المساعد -> اختبار -> نشر. المراحل غير المتاحة تظهر next/setup؛ التقدم محفوظ في backend وليس localStorage وحده.
6. ضع Screen Map يحدد لكل route الدور والهدف والـprimary action ومصدر البيانات والحالات الفارغة والخطأ والجزئية. صحح بنية المعلومات قبل تكرار تصميم عشر صفحات.

## الاختبارات المطلوبة

- Story/component tests للسلوك المهم، وPlaywright على 360/390/768/1280/1440 في العربية والإنجليزية.
- axe-core مع فحص يدوي للوحة المفاتيح والمودالات وترتيب التركيز والـscreen reader labels؛ فحص تباين الألوان.
- اختبار حفظ onboarding وتحديث الصفحة/العودة وعدم ازدواج إنشاء المتجر، وأخطاء API وإعادة المحاولة.
- screenshots مرجعية تُراجع بصريًا قبل اعتمادها؛ لا تعتمد على snapshot pixel وحده لإثبات صحة UX.

## القبول

رحلة دخول وإعداد مفهومة وقابلة للاستمرار بلا overflow أو نصوص مقصوصة أو عناصر غير قابلة للنقر بالهاتف. التقارير تفرق بين فحص الوصول الآلي واليدوي، وبين خط نهائي وfallback تطوير.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
