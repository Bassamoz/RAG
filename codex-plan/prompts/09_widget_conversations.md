# المرحلة 09: نافذة المحادثة والسياق والتحويل وتوقيت الرد

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 08. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R27، R28، R29، R47.

## العمل المطلوب

1. نافذة قابلة للتضمين بصورة آمنة وخفيفة مع name/logo/colors ضمن التخصيص، تحية وأسئلة مقترحة وبطاقات منتجات ومصدر عام مناسب وتقييم وزر موظف. لا تعرض أسماء ملفات داخلية أو traces للعميل.
2. إنشاء جلسة زائر مرتبطة بالمتجر، origin allowlist وsigned/opaque conversation token وصلاحيات ضيقة وحدود abuse. لا يحمل embed public ID إذن قراءة محادثات سابقة. تحقق postMessage وiframe/CSP بحسب تصميم النشر.
3. persistence وcursor pagination للرسائل، idempotent send، حالات accepted/processing/answered/failed، reconnect وإعادة محاولة آمنة. status streaming حقيقي؛ المحتوى النهائي يفحص قبل وصوله.
4. state machine bot_active/handoff_pending/human_active/resolved، وحجز version/epoch يوقف ردًا قيد التوليد عند takeover. sender=agent من الخادم فقط. إلغاء الرد المجدول أو القديم عند تغيير الحالة أو حذف المحادثة.
5. timing policy للبحث configurable: أول رد 15–120 والتالي 15–60 ثانية ضمن سيناريو اختبار، وproduction بلا intentional delay افتراضيًا. استخدم scheduler غير blocking؛ fake clock للاختبار. ACK وحالة معالجة واقعية، ولا تؤخر الموظف أو تعِد نافذة الأولى لكل رسالة.
6. سياق محدود ومراجع معرفية يعاد التحقق منها؛ session reset وتاريخ احتفاظ. Widget لا يجمع رقمًا أو بريدًا بلا غرض واضح؛ تعريف الطبيعة الآلية متاح.
7. صفحة installation مع snippet حقيقي ومعاينة واختبار ظهور، وشرح Salla/Zid snippets ومستند تهيئة متجر خاص. استعمل نفس API للمحادثة في كل القنوات.

## الاختبارات المطلوبة

E2E embed في موقع اختبار مستقل origin، هاتف RTL/LTR، منع الوصول بمحادثة متجر آخر، إعادة اتصال وتكرار submit، XSS في Markdown/links/product titles، postMessage مزور.

race: موظف يستلم أثناء generation أو retry -> لا يصل رد البوت؛ زائر يرسل سؤالًا جديدًا أثناء تأخير -> لا جواب قديم ملتبس؛ fake-clock أول/ثاني/رسالة إنسانية؛ حذف جلسة مع job معلق.

## القبول

زائر يحاور المساعد في متجر الاختبار ويطلب موظفًا، ويحفظ السجل ويستأنف بأمان. التوقيت والآثار الشبكية موثقة ولا تُقاس مهلة التأخير كزمن النموذج.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
