# المرحلة 10: WhatsApp Business والتحقق من رقم الاتصال

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 09. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R30، R31، R32، R47.

## العمل المطلوب

1. واجهة رقم اتصال التاجر منفصلة: E.164، إرسال تحقق عبر مزود مدعوم مهيأ، إدخال OTP، verified_at، تغيير الرقم مع إعادة تحقق وتدقيق. لا تشترط شراء Twilio إذا توفر مزود مكافئ مدعوم، ولا تبنِ توليد OTP مخصصًا.
2. قناة WhatsApp Cloud API: حالات not_connected/connecting/pending_approval/active/error/disconnected. تكامل onboarding رسمي وEmbedded Signup إذا متاح، مع التحقق من assets المخولة وWABA/phone_number_id. زر «ربط» لا ينفذ update status محليًا فقط.
3. راجع وثائق Meta الحالية والـGraph version والpermissions ومراحل مراجعة التطبيق. نفذ تبادل tokens الخادمي وتخزينها المشفر وربط القناة بtenant/store. إعداد test number رسمي واضح للتطوير، وlive مختلف عنه.
4. webhook challenge والتحقق cryptographic للـraw body بالطريقة الرسمية، inbox متين وdedup/provider IDs وevent ordering. رفض طلب مزور قبل معالجته. الاشتراك/الفصل عن القناة لهما أثر حقيقي.
5. incoming text يمر عبر منسق المرحلة08 وآلة حالات09، وoutbound عبر outbox مضبوط. customer service window والقوالب المعتمدة وموافقة الاستقبال وopt-out وفق الوثائق الحالية، والامتناع عن إرسال غير مسموح.
6. statuses sent/delivered/read/failed/unknown؛ retry/reconcile حسب ضمانات المزوّد. لا تكرر إرسالًا عند timeout غير معلوم التسليم. سجل أخطاء آمنة واسم قالب/لغة دون نص شخصي زائد.
7. واجهة قناة واختبار اتصال وحالة webhook واختبار إلى رقم مملوك موافق، وربط inbox ورسائل الموظف بالقناة نفسها. المرفقات غير المدعومة تعالج برسالة واضحة أو تحويل، لا تجاهل صامت.

## الاختبارات المطلوبة

اختبارات رقم invalid/خطأ/منتهي/مكرر وrate-limit. contracts لOAuth/onboarding/tokens، signature خاطئ وreplay، WABA غير مخول وphone ID لمستأجر آخر، حدث مكرر وحالات out-of-order.

اختبار نافذة الخدمة بالساعة عند الحد وتجاوزه، قالب غير معتمد/لغة غير متاحة، opt-out، sending timeout وunknown، takeover أثناء الإرسال. smoke حي: رقم اختبار مصرح يرسل رسالة -> جواب موثق -> وصول status -> طلب موظف ورد الموظف.

## القبول

إثبات القناة يأتي من المزوّد لا من كتابة الرقم. إن غابت موافقات Meta أو credentials أكمل الكود والاختبارات المحلية وسجل العائق، ولا تقل إن WhatsApp production يعمل.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
