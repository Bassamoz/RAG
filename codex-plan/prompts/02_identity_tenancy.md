# المرحلة 02: البريد برمز تحقق والجلسات والصلاحيات والعزل

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 01. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R04، R05، R06، R07، R47.

## العمل المطلوب

1. نفذ دخول/تسجيل Email OTP باستخدام Supabase Auth عبر BFF server-only كما في المواصفات. صمم واجهات البريد والرمز والتحقق وإعادة الإرسال والفشل. لا جلسة قبل verifyOtp ناجح ولا Magic Link بدل طلب المستخدم.
2. أنشئ session store آمنًا وcookies وCSRF وJWT validation وتجديدًا مقفلًا وإبطالًا على logout/role change/account disable. اختبر الفصل بين session في التطبيق وtokens المزود؛ لا مكشوفات localStorage.
3. أنشئ المنشأة وعضويات الأدوار والدعوات وتبديل المنشأة. سياسة tenant_owner والأدوار النظامية في الخادم؛ body لا يمنح role أعلى. نطاق platform_admin منفصل ومقيد ومدقق.
4. نفذ TOTP enrollment/challenge/unenroll مع إعادة تحقق، وAAL2 للأدوار الحساسة، وسياسة recovery موثقة لا تتجاوز العامل. جرد الجلسات وإلغاء جلسة مختارة/الجميع، وتغيير البريد بتدفق رسمي.
5. طبق RLS ودور تشغيل غير متجاوز للصلاحيات على الجداول الحالية. tenant context من هوية/عضوية متحققة داخل المعاملة؛ لا يعتمد على user_metadata قابلة للتعديل. اختبر connection pool والوظائف الخلفية.
6. جهز SMTP وقالب بريد وMailpit/الصندوق المحلي للاختبارات؛ وثق تجربة الإنتاج الحية المطلوبة. لا تعتبر إرسال ناجح من SDK دليل وصول بريد.

## أكواد الاختبارات المطلوبة

`test_email_otp_flow`، `test_session_revocation`، `test_refresh_races`، `test_mfa_assurance`، `test_membership_permissions`، `test_rls_tenant_isolation`، وE2E دخول ودعوة وتبديل منشأة.

غطِّ رمزًا خاطئًا/منتهيًا/مستخدمًا وإعادة إرسال وحدود محاولات، البريد غير المتحقق، enumeration، CSRF وopen redirect، JWT مزورًا/منتهيًا/wrong audience، دعوة لبريد غير مطابق، إزالة آخر مالك، موظفًا يرفع دوره، وصلاحية أُبطلت بينما JWT لم ينته.

اختبار RLS بقاعدة حقيقية ودور التشغيل: مستخدم A لا يقرأ/يكتب tenant B، وفحص اتصال pool استُخدم سابقًا لمستأجر آخر. غياب secret يحجب smoke الحي ولا يجعله ناجحًا.

## القبول

يمكن لمستخدم اختبار دخول حسابه بالرمز وإنشاء منشأته؛ الأدوار والحالات السلبية مثبتة. منصة غير مهيأة للبريد تعرض setup واضحًا، ولا يوجد bypass إنتاجي لتسهيل العرض.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
