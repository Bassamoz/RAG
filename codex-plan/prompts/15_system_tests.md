نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 14. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R03، R07، R42، R43، R47.

## العمل المطلوب

1. راجع مصفوفة التتبع واختبارات المراحل السابقة؛ أكمل الفجوات في الرحلات الحرجة، دون إعادة كتابة اختبارات تعمل أو إضافة checks تطابق implementation بلا قيمة.
2. جهز pytest unit/integration/property-based للحدود الحرجة، fixtures حقيقية لـPostgres/pgvector/Redis، Vitest/Testing Library، وPlaywright لكل دور. seed حتمي قابل للتنظيف ولا بيانات عملاء حقيقية.
3. E2E رئيسي: تسجيل بريد -> OTP -> منشأة -> متجر -> استيراد -> معرفة واعتماد -> سؤال موثق -> تحديث منتج -> سؤال جديد -> تحويل لموظف -> رد وتقييم -> تقرير -> حذف/استرجاع.
4. رحلات إدارة فريق ودعوات وMFA وتغيير بريد/رقم وربط/فصل متجر وواتساب. افصل سيناريوهات sandbox والعقود عن E2E الحية واظهرها في التقارير.
5. load بـk6 وفق budgets المعتمدة: مستخدمون متزامنون، محادثات/second، حجم corpus/متاجر، مدة ramp/steady، وأجهزة محددة. قس latency p50/p95/error rates/queue lag/CPU/RAM/DB connections/token cost. لا تعتبر mock LLM قياسًا لسرعة النموذج الحقيقي.
6. resilience: انقطاع DB/Redis/AI/connector، worker crash وسط import، duplicate jobs، stale caches، connection loss في widget، retry بعد response timeout، refresh tokens سباق، takeover أثناء generation، deletion أثناء indexing.
7. اختبارات migration من نسخة سابقة وjobs قديمة وعقد API generated client، وفحص backup/restore المستقل. اكتب runbooks لفشل المزامنة وإعادة التشغيل دون فقد/تكرار.
8. coverage تقرير مساعد لا هدف وحيد؛ غطّ branches الحساسة والصلاحيات والسياسات. كرر فحوص flakiness ذات السلوك المتزامن مع timeouts معقولة، وأصلح السبب بدل sleep طويل أو retry يخفي عيبًا.

## المخرجات والقبول

أكواد اختبار قابلة للتشغيل وأوامر واحدة لكل suite، JUnit/HTML وأدلة E2E/screenshots منزوعة الأسرار وتقارير load. جميع acceptance paths المطلوبة لها دليل أو blocker محدد. صفر تسرب مستأجرين في المجموعة الحرجة شرط مرور؛ لا يعني ذلك إثبات غياب كل ثغرة ممكنة.

إن لم تبلغ الميزانيات، حلل السبب وحسّن أو صرّح بحد السعة الفعلي. لا تغير workload أو عتبة القبول بعد الفشل دون قرار موثق ومقارنة جديدة.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
