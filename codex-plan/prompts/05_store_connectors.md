# المرحلة 05: الربط مع سلة وزد والمتجر الخاص والمزامنة

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 04. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R12، R13، R14، R15، R25، R47.

## العمل المطلوب

1. طبق Connector interface محدودة وcapability matrix، ثم SallaConnector وZidConnector فعليين وفق وثائقهما الحالية. لا تبنِ موصلًا عامًا بافتراض أن headers/endpoints/scopes متطابقة.
2. واجهة رابط المتجر واكتشاف مبدئي قابل للتصحيح، OAuth authorization/callback/state، تبادل وتجديد tokens على الخادم، revoke/disconnect/health. اربط external_store_id بالمالك الصحيح وامنع reuse عبر مستأجرين.
3. استيراد المنتجات والمتغيرات والصور والعملة والتوفر المتاح والعروض ذات الصلاحية وفق capability. pagination/checkpoints ومزامنة differential مع progress وعدد نجاح وفشل وآخر مزامنة.
4. تحقق webhooks بآلية كل مزود، احفظ inbox متينًا ثم ACK مناسبًا، وعالج في worker مع idempotency وoutbox. توقيع صالح ليس ضمان حداثة الحدث؛ افحص versions/time وأعد جلب المصدر عند التباس ترتيب الأحداث.
5. retries/backoff وRetry-After وlimits لكل متجر، refresh lock، scheduled reconciliation، حذف/إخفاء منتج، ومشكلة صلاحية منتهية تعرض إعادة الربط. لا تُسقط الفشل في logs فقط.
6. Custom API موثقة مع mappings وحدود URL/SSRF وأسرار خادمية. CSV يبقى مسارًا كاملًا عند غياب API. قراءة الصفحات تنفذ في المرحلة06، ولا تَعِد باستخراج كامل لأي موقع.
7. أضف health panel واختبار اتصال وفصل الربط وتعليق المزامنة وإعادة المحاولة. وثق حسابات الشركاء ومتطلبات scopes وعمليات نشر التطبيقات دون ادعاء موافقة لم تحدث.

## الاختبارات المطلوبة

Contract fixtures مأخوذة من أمثلة رسمية أو sandbox منزوعة الأسرار، وtransport mocks لخطأ401/403/429/500/timeout وpagination فارغة/متكررة. OAuth state خاطئ/منتهي/معاد وredirect غير مسموح، متجر مرتبط لtenant آخر، وtoken refresh متزامن.

Integration لحدث مكرر/متأخر/حذف/انقطاع worker. تجربة حية مستقلة لكل من سلة وزد: تفويض -> استيراد -> تعديل منتج في المتجر التجريبي -> تحديث نسختنا -> فصل الربط. لا تعِد توليد تمثيل كل الوصف لمجرد تغير سعر إن كان السعر خارج النص الدلالي.

## القبول

الكود يدعم الموصلين، ويعرض الاتصال الحقيقي فقط بعد التحقق. كل تجربة حية غير منفذة تبقى blocked_external حتى لو مرّت contracts. لا تستخدم scraper بدل OAuth لتجاوز غياب صلاحية.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
