# المرحلة 11: مساحة الموظف والتذاكر والتنبيهات والإدارة

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 10. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R28، R33، R34، R47.

## العمل المطلوب

1. inbox بثلاث مناطق مرنة: قائمة المحادثات، الحوار، معلومات السياق. فلاتر assigned/unassigned/status/channel/time، بحث محدود النطاق، pagination وrealtime status دون تحميل كامل السجل.
2. استلام وتحويل وتعيين موظف وإغلاق وإعادة فتح، وصلاحيات واضحة وسجل أحداث. تعارض تعيين موظفين يُحل optimistic lock أو transaction بدل last-write-wins صامت.
3. تذاكر مرتبطة بالمحادثة: عنوان وسبب وأولوية ومسؤول وحالة وتعليقات ومهام متابعة. ملاحظة داخلية لا تُرسل للعميل ولا تدخل corpus العام. إدخال تذكرة إرجاع ليس تنفيذ refund أو إلغاء طلب.
4. business hours ومنطقة زمنية وتوفر فريق ورسائل خارج الدوام، وتوقعات لا تتجاوز إعدادات التاجر. ملخص handoff يحافظ على الأدلة والحد الأدنى من البيانات.
5. مركز تنبيهات unread/read/preferences، وإشعارات بريد للموظفين المصرح لهم فقط عند تهيئة SMTP؛ أرقام غير مأذونة لا تتلقى رسائل. ربط التنبيه بحدث واحد idempotent، وعدم تضمين أسرار أو جسم محادثة كامل في البريد.
6. إدارة الفريق والدعوات الحالية دون إنشاء auth آخر، وحدود access لكل دور. لوحة platform_admin للصحة والعوائق واستهلاك المنصة والتعليق/الاستعادة بصلاحيات وتدقيق؛ لا كشف تلقائي لمحادثات جميع المتاجر.
7. مراجعة رد غير مناسب وتحويله إلى اقتراح معرفة draft مع اعتماد إنساني؛ لا تعلم تلقائي من إجابة خاطئة أو ملاحظة موظف خاصة.

## الاختبارات المطلوبة

E2E زائر -> تحويل -> موظف يستلم -> يرد -> يغلق -> تقييم. تعيينان متزامنان، عضو مُعلّق، analyst يحاول الرد، agent يحاول تعديل قنوات/أسرار، ملاحظة داخلية لا تظهر في widget/WhatsApp/exports غير المخولة.

اختبار أوقات دوام/timezone، duplicate notification، نقر تنبيه لمتجر ليس للعضو، وقناة بريد معطلة دون فقد التنبيه الداخلي. تحقق حقول حزمة التحويل والسبب.

## القبول

خدمة العملاء قابلة للعمل من بدايتها لنهايتها، وتوقف البوت أثناء التدخل البشري مثبت. كل زر تشغيلي له أثر ودليل وصلاحية، ولا توجد لوحات أرقام ثابتة.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
