# المرحلة 01: المستودع والبيئة وقاعدة البيانات والعقود

أنت مسؤول تنفيذ هذه المرحلة داخل المشروع الحالي. اقرأ تعليمات المستودع، و`codex-plan/MASTER_SPEC.md` و`codex-plan/RESEARCH_MAP.md` و`codex-plan/REQUIREMENTS.md`، ثم `docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` وقرارات ADR إن وجدت. افحص الموجود وأكمله؛ لا تبدأ تطبيقًا آخر ولا تعِد scaffold ولا تستبدل migrations قائمة.

نفذ الواجهة والخلفية والتخزين والصلاحيات واختبارات السلوك المطلوبة لهذه المرحلة فعليًا. ارجع إلى الوثائق الرسمية للمكتبات والمزودين قبل استخدام API. خذ القيم الافتراضية والحدود من MASTER_SPEC؛ أي تغيير قرار له ADR وتحديث العقود، لا تغيير صامت.

**الاعتماد:** تستكمل المراحل 00 إلى 00. تحقق من الأجزاء السابقة التي تعتمد عليها؛ يمكن تجهيز عمل مستقل عن خدمة محجوبة مع إبقاء اختبار الربط محجوبًا.

**المتطلبات:** R02، R03، R07، R47.

## العمل المطلوب

1. أنشئ/أكمل بنية بسيطة: `apps/web`، `apps/api`، `packages/api-client`، `infra`، `scripts`، `tests`، `docs`. موضع widget يوضع في الواجهة أو حزمة مستقلة عند الحاجة؛ لا backend مستقل لكل وحدة.
2. ثبّت pnpm وPython/uv وإصدارات متوافقة في lockfiles. أضف lint/format/typecheck وبيئات dev/test/staging/prod والتحقق من الإعدادات عند بدء التشغيل. أخطاء secrets الناقصة تكون آمنة وواضحة.
3. أنشئ health/readiness منضبطين، logging منظم بـrequest_id، معالجة أخطاء موحدة، حدود request body، وعقد OpenAPI أولي وعميل TypeScript مولد.
4. أنشئ مخطط التطبيق وmigrations الأولى للحسابات والمنشآت والمتاجر فقط حسب التصميم، وpgvector extension، ودور تشغيل محدود؛ أضف RLS context pattern مبكرًا. Alembic مالك migrations مخطط التطبيق؛ لا يدير auth schema المملوك للمزوّد عشوائيًا.
5. جهز Postgres/Auth/Storage محلية عبر Supabase local إن أمكن، وRedis وworker من نفس الكود عبر Docker. اكتب `make dev` أو script مكافئ، ولا تشغّل PostgreSQL تطبيق ثانية بلا سبب.
6. جهز test fixtures مع بيانات اصطناعية وبيئات معزولة؛ production لا يعمل بزرع بيانات demo تلقائيًا. أضف CI أوليًا و`.env.example` دون أسرار، وignore للملفات والأوزان والنسخ الكبيرة.

## الاختبارات المطلوبة

- تثبيت من clean checkout بأوامر README، ثم تشغيل مرتين دون إتلاف البيانات.
- migration على DB فارغة، ثم إعادة تشغيلها، ثم الترقية من snapshot اختبار سابق حين توجد نسخة سابقة.
- فشل الإعداد عند نقص متغير حرج، وعدم تسريب قيمته؛ health لا يسرّب تكوينًا حساسًا.
- اتصال DB/Redis/worker حقيقي في integration test؛ فشل خدمة لا يظهر readiness صحيحًا.
- contract/typecheck للتطابق بين OpenAPI وعميل الواجهة.

## القبول

المشروع يبدأ من بيئة موثقة، والواجهة والخلفية والعامل يستطيعون العمل معًا. توجد اختبارات smoke حقيقية وبنية توسع موضعية، دون صفحات ميزات وهمية أو هياكل microservices فارغة.

## طريقة التحقق والتسليم في هذه المرحلة

- اكتب أكواد الاختبارات في المستودع، وشغّل الفحوص المتأثرة فعلًا. تحقق من النتائج وأصلح الفشل ثم أعد الفحوص اللازمة فقط. لا اختبارات تؤكد mock فحسب ولا تعطيل assertions أو security rules لتمرير النتائج.
- سجّل الأمر الفعلي والنتيجة وexit code والبيئة ونسخة الكود ومسار artifact. افصل اختبارات الوحدات والعقود عن اختبار المزود/النموذج الحي. نقص المفاتيح يسجل `blocked_external`، ولا يعادل نجاحًا.
- حدث `docs/REQUIREMENTS_TRACEABILITY.md` و`docs/PROJECT_STATE.json` و`docs/NEXT_ACTIONS.md` و`docs/IMPLEMENTATION_EXPLAINED_AR.md` وتقرير المرحلة في `docs/phase-reports/`. لا تخزن أسرارًا أو بيانات شخصية في الأدلة.
- تقرير Markdown بالعربية يوضح: المشكلة التي حلت، الملفات والوحدات، كيف تتدفق البيانات، القرارات، تعليقات الكود المهمة، أوامر التشغيل والاختبارات، ما نجح وما فشل وما لم يُختبر ولماذا، والجزء التالي بدقة.
- راجع diff واحذف الكود الميت والتكرار والمكتبات التي لم تعد لازمة لهذه المرحلة دون الإضرار بعمل المستخدم. اترك المشروع قابلًا للاستمرار.
- لا تنتقل تلقائيًا إلى مرحلة أخرى. إذا انقطع السياق، احفظ checkpoint للعمل المكتمل وأول خطوة باقية. لا تدّع اكتمال مرحلة أو جاهزية نشر قبل أدلة قبولها.
